# Experiment Charter 0001: Source Navigation and Assistant Cost

**Status:** Proposed

**Purpose:** Determine whether existing source-navigation tools materially reduce the time, context, and tool calls required for coding assistants to work on WildFly, and identify which WildFly-specific relationships require additional indexing.

This charter is deliberately narrower than the final architecture investigation. It is a measurement plan. It does not select SCIP, JDT, Bob Tags, MCP, CI artifacts, or any storage model.

## Objective

Measure the end-to-end cost and usefulness of these approaches:

1. ordinary repository exploration using `rg`, directory listing, and file reads;
2. Bob-style materialized lookup files for declarations, method ranges, and likely callers;
3. SCIP generated by `scip-java`;
4. Eclipse JDT Language Server queries.

The question is not whether one tool produces the most complete graph. The question is:

> Does the tool help an assistant complete representative WildFly tasks with less total cost and no unacceptable loss of correctness?

## Non-goals

This experiment will not:

- implement a production index generator;
- modify WildFly satellite repositories;
- make AI-context files a prerequisite;
- select a final artifact format or cache location;
- build a remote service or MCP server;
- compare every code-analysis framework;
- treat approximate caller results as semantically resolved call graphs.

Kythe, CodeQL, SootUp, OpenGrok, and other tools remain follow-up candidates. They should only be added if the first experiments expose a requirement they are designed to solve.

## Repositories and source states

Use local checkouts of:

- `wildfly-core`;
- `wildfly`.

Start with a small representative module from each repository, then test a full reactor only if the tool remains practical.

Run the useful subset of experiments against:

- a clean current development checkout;
- one maintenance branch;
- one SNAPSHOT branch or version;
- a dirty worktree with an uncommitted source edit;
- a repository with no AI-context files.

The experiment must record exact repository path, branch/ref, commit SHA, Java version, Maven version, tool version, and whether the worktree was dirty.

## Candidate conditions

### Baseline: ordinary exploration

The assistant may use the repository files, `rg`, directory listing, and bounded file reads. It receives no generated source index.

### Bob-style lookup

Use existing Bob Tags behavior or a disposable equivalent where practical. Measure declarations, exact method ranges, and likely callers separately. Record any Open Liberty-specific assumptions, Universal Ctags requirements, source-discovery gaps, and setup cost.

Do not treat this condition as a commitment to reuse the Bob Tags implementation.

### SCIP

Use `scip-java` to produce a SCIP artifact where the repository and build permit it. Record all build commands, cleanup or compilation side effects, dependency resolution, unresolved symbols, and cross-module behavior.

Expose only the minimum read-only lookup operations needed by the tasks. Do not build a general SCIP platform for this experiment.

### JDT Language Server

Use JDT Language Server for definition, references, type hierarchy, and call hierarchy where supported. Record workspace import time, memory or stability problems, Java-runtime requirements, and behavior with incomplete or dirty source.

## Task corpus

Begin with eight task cards. Each task must have an expert-reviewed expected set of relevant files or concepts.

1. Locate the implementation of a management operation.
2. Find a method implementation and its relevant tests.
3. Find likely callers of an operation handler.
4. Trace a subsystem extension to its resource definitions.
5. Locate the source and callers of a WildFly log message.
6. Trace a service installation to likely consumers.
7. Trace a Galleon layer or provisioning entry to the runtime code it affects.
8. Follow a cross-repository relationship between `wildfly-core` and `wildfly`.

For every task, record:

- task wording shown to the assistant;
- repository and revision;
- expected relevant files and concepts;
- permitted tools for each condition;
- completion criteria;
- known ambiguity or approximation;
- reviewer responsible for judging correctness.

The task corpus should use real existing code, not invented fixtures, except for a small controlled fixture used to test overloads, inheritance, and dirty-file behavior.

## Execution protocol

Use the same assistant model, task wording, repository revision, and source visibility for every condition.

For each condition:

1. Run a cold trial with no pre-existing generated index or workspace state.
2. Run a warm trial with the generated state already available.
3. Repeat important tasks enough to distinguish noise from a real effect.
4. Randomize condition order where practical.
5. Give each tool a concise, equivalent usage guide.
6. Capture the complete tool transcript outside the repository.
7. Have a WildFly-aware reviewer judge the final result without assuming the tool was correct.

If a tool cannot run, record the failure as evidence. Do not silently replace it with a hand-built implementation.

## Measurements

Capture these metrics for every task:

- completed correctly: yes/no/partial;
- wall-clock time, including index generation when applicable;
- model input tokens, if available;
- number of assistant tool calls;
- number of source files opened;
- number of source lines read;
- number of irrelevant files or ranges opened;
- time to first relevant file or concept;
- incorrect or misleading results;
- index/workspace generation time;
- generated artifact size;
- network access and downloads;
- source checkout changes or build side effects.

The primary comparison is total cost:

```text
total cost = setup + generation/import + assistant task execution
```

Also calculate the approximate break-even number of tasks:

```text
break-even tasks = one-time generation cost / per-task savings
```

## Freshness checks

At minimum, verify behavior after:

- changing a method body without changing its name;
- adding a method;
- deleting a source file;
- renaming a source file;
- switching branches;
- editing an uncommitted file;
- changing a generated-source or dependency input where relevant.

Record whether the tool detects stale data, regenerates automatically, warns the user, or returns misleading locations.

## Results format

Each completed experiment should produce a concise findings document containing:

```text
Hypothesis
Environment
Conditions tested
Measured results
Correctness review
Failures and limitations
Evidence confidence
Architectural consequence
Follow-up experiment
```

Do not commit raw transcripts or generated indexes. The findings document should contain summary tables and links to externally stored raw evidence when available.

## Decision rules

The experiment should recommend an approach only when it has evidence for both usefulness and operational viability.

Possible outcomes include:

- ordinary search is sufficient for the first prototype;
- Bob-style materialized ranges provide most of the benefit;
- SCIP provides valuable semantic data and should be materialized for assistants;
- JDT is the best interactive local integration;
- generic Java tools help, but WildFly-specific enrichment is required;
- index generation cost or freshness problems outweigh the benefits;
- a deeper CodeQL, Kythe, or SootUp experiment is justified.

Do not interpret “more precise” as automatically “better.” A slower or harder-to-install tool must demonstrate a task-level benefit.
